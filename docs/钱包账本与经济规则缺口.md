# 钱包账本与经济规则缺口

依据方案 7.2、7.3 与原 diamond/club 消费者。此阶段交付内部事务基础设施和只读/核对后台，不声明原兑换、充值、圈费用已确认，也不开放原关闭奖励。

## 内部一致性

- 账户键由 PERSONAL/CLUB/SYSTEM 主体、主体 ID、card/diamond 币种组成。个人和圈账户区分可用与冻结，始终非负；系统清算账户承载每币种的对手分录，不作为可兑付玩家余额。
- 每个内部命令必须有来源依据、规则版本和稳定 business_key。该键必须由业务订单、资格或结算编号得出；服务端临时 UUID 本身不能识别旧客户端重试。
- 分录按账户归并、排序并检查每币种借贷平衡，不把房卡和钻石直接相加。划转、冻结、释放有各自方向约束。余额不能超出现有 JavaScript 精确整数范围。
- 同一业务键取得排他锁后检查规范化请求摘要：相同命令回放原收据；不同内容拒绝。账户按固定顺序锁定，余额、版本、流水、完成标记同事务提交。
- 重放收据保留首次提交时的余额，不代表重放时的最新余额；未来旧接口适配器必须在确认订单后重新查询权威余额，不能把历史收据直接覆盖到当前客户端资产。
- 迁移记录明确的期初快照，后续对账以期初加全部流水比较当前可用/冻结。该快照不是迁移前历史账本。新账户从零开始，不生成赠送或初始收益。
- 后台核对使用一致性读，只生成核对记录和审计；差异保留待核查，不静默调账。核对并发最多 2 个，完整汇总 SQL 有 5 秒期限。未实现每日全量任务，不宣称已具备全部保留/恢复策略。

## 已接入的后台范围

资产账本按个人 UID 或圈 ID、币种和最多 31 个北京时间自然日查询，使用主体/币种/时间索引。个人账本要求平台数据范围；圈账本支持独立 CLUB 数据范围；账本查询和核对权限分开。无直接编辑余额、删除流水、手工发币或兑付接口。

## 尚缺业务依据

- 原源码的 getExchangeRate 消费 exchange_ratio，页面存在默认 7；这只能证明客户端回退值，不能作为原站权威汇率。兑换方向/数量单位、手续费、最低数量和可逆性仍待确认。
- 旧 role/exchangeCard、role/exchangeDiamond、club/exchangeCard、club/exchangeDiamond、transferDiamond、transferCard、transferToClub 未带可复用订单号。不能以相同金额时间窗或者每次生成不同 UUID 宣称精确防重，启用策略需确认。
- 创建圈转入额、圈改名/升级费用、解散退款接收和冻结资金处理，以及 6003 扣费时点、AA/房主支付与未开局退款仍待确认。
- 真实资金补偿必须另做申请人与复核人不同的审批流程，并有原订单/流水依据；此阶段不提供补偿执行入口。
- 奖励、商品、充值、提取的资格/定价/供应商均不由账本内核创造。测试中的奖励和清算仅在隔离 Testcontainers 数据库里验证事务，不能作为上线业务规则。

所有未确认的兑换和圈资金入口明确返回不可执行，不改资产。测试夹具不得向本地运行库或生产库发放展示余额。
