ConfirmedBusinessRules.VERSION 为 user-rules-20261107-v1。兑换计划必须由后续业务适配器传入已认证 UID 与持久订单编号，不能每次接到旧请求就新造 UUID 冒充防重。当前仅内部计划，账本组合用例已经在本轮 212 项实际 Java 测试中通过，不开通旧兑换写入。

这些积分不是房卡或钻石，计算结果不等于已经结算入库。公开建房、叫分阶段、累计积分/终局原报文、原客户端三人联机及扣费仍需衔接，不能用本次计分器宣布整场游戏已经交付。

## 原兑换页的实际兼容性阻碍

旧 diamond 页面把 exchange_ratio 定义为“每房卡需要多少钻石”。新规则在该字段中需要 0.1，而原 getYu 使用 JavaScript 浮点 %，getShang 使用 (数量-余数)/比例；实际只读复现中，1 / 2 / 10 钻石分别显示 9 / 19 / 99 房卡。

实际运行文本资源位于 Client/creator/assets/source-data/files/f8c877d2a7955b105dc3ccb2cc3bf2b7e17fc088d1ed81b680d8f1a9ee4c12c9.txt。脱敏源码表达式、摘要与样本见 evidence/exchange-client-compatibility.json，复现命令 node tools/check-exchange-client.mjs。没有运行归档脚本或修改客户端。

目前仍遵守方案 1.2 的“Creator 除服务器地址外保持原样”。既不能把 exchange_ratio 填成 10 颠倒用户规则，也不能填 0.1 后让错误的页面显示参与实际资产操作。后端保留精确的 1→10 计划，旧页面和缺少订单标识的跨重连重试仍待适配；客户端例外修改须由用户明确授权。
